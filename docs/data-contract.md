# Menu data contract

The public site loads `data/menu.json` and `data/translations.json` using relative URLs.

Menu schema version 1:

```json
{
  "schema_version": 1,
  "source": {"url": "https://www.stw-saarland.de/gastro/mensa-saarbruecken/", "fetched_at": "2026-09-21T10:00:00Z", "sha256": "hex"},
  "coverage": {"start": "2026-09-21", "end": "2026-10-02"},
  "days": [{"date": "2026-09-21", "meals": [{
    "id": "stable-date-category-title-hash",
    "translation_key": "content-hash",
    "category": "Wahlessen",
    "location": "Aufgang C",
    "name_de": "Vegan: Ägyptisches Kushari",
    "components": [{"name_de": "Reis", "notices": []}],
    "notices": ["vegan", "Weizen"],
    "prices": {"student": 350, "staff": 465, "guest": 535},
    "price_status": "verified",
    "price_source": {"date": "2026-09-21", "category": "Wahlessen", "name": "Vegan: Ägyptisches Kushari", "raw": "S: 3,50 | M: 4,65 | G: 5,35"}
  }]}]
}
```

Prices are integer euro cents, extracted only from the same source meal. A source meal without a price block uses `prices: null`, `price_status: source_pending` and `price_source.raw: null`. The UI links to the source rather than claiming the cafeteria has no price. Malformed/partial price blocks fail collection. An existing same-date/same-category/same-name priced record becoming unpriced fails collection. No price is copied from another date, category or dish. Information entries are excluded from meals. All original component and meal notices are retained.

Meal IDs use the ISO date and SHA-256 of canonical compact sorted-key JSON containing `date`, `category`, and `name`. If the source repeats an identical date/category/name, every entry is retained; later occurrences receive `-2`, `-3`, and subsequent suffixes in source order. Duplicate IDs are invalid. Collection independently reconciles raw meal, metadata, component, notice, and price token inventories with extraction. Updates reject missing previously covered dates inside the new coverage range and losses exceeding one quarter of a previously published overlapping day's meals; these source changes require review before publication.

Translation cache schema:

```json
{"schema_version": 1, "entries": {"content-hash": {
  "source": {"name_de": "German dish", "components": ["German side"]},
  "en": {"name": "English dish", "components": ["English side"]},
  "ko": {"name": "한국어 요리", "components": ["한국어 곁들임"]},
  "origin": "reviewed-draft",
  "model": "assistant-draft",
  "prompt_version": "menu-v1"
}}, "notices": {
  "Weizen": {"en": "Wheat", "ko": "밀"},
  "Milch und Laktose": {"en": "Milk and lactose", "ko": "우유 및 유당"}
}}
```

`translation_key` is SHA-256 of UTF-8 JSON `{"name_de": ..., "components": [...]}` with sorted keys, compact separators and `ensure_ascii=False`; components are names only, in original order. A source change yields a different key. Notices and prices are not generated by a model. With no API configured, unknown dish translations remain German and are explicitly identified as original text. Initial cached translations are editorial drafts, not claimed as Gemma output.

Korean/English primary titles describe the dish; exact German names remain separate subtitles. The reviewed naming policy removes `mensaVital` and `KlimaTeller` campaign prefixes and uses descriptive translations for known opaque dish names. It applies to existing cache entries as well as new editorial/model results, including a refresh without an inference provider. An entry whose title is changed by this policy records `name_policy_version: "semantic-names-v1"`; its original `origin`, `model` and `prompt_version` still identify generation provenance. Component translations, source strings and source hashes are not changed by the naming policy. Publication validation rejects unresolved campaign/opaque names, so malformed or incomplete normalization cannot silently replace the published snapshot.

The naming-policy migration keeps `menu-v3` generation results reusable after normalization; `menu-v4` is used for new translations. The worker and cache builder share the same reuse rule so a naming-only migration does not start inference or replace existing component translations with editorial drafts. A missing source key, unsupported generation version or changed model still requires the usual translation path.

The optional top-level `notices` object keeps translation cache schema version 1 backward compatible with older caches. Each key is an exact source German notice string, including source spelling; each value contains exactly nonempty `en` and `ko` strings. Meal and component `notices` arrays in `menu.json` remain unchanged. The UI shows the selected-language notice alongside the German original, and marks an unknown notice as untranslated while retaining its original text.

`data/notice-translations.json` is the reviewed bilingual glossary for fixed ingredient, dietary, allergen and additive labels. Cache builds translate every current meal and component notice independently of dish cache hits and retain earlier notice keys for interrupted-snapshot compatibility. Unknown source labels reject the entire candidate before model inference or snapshot writes, with an error naming the labels and glossary path. A reviewer must add the exact German label and its English/Korean translations before retrying. The worker publication check and CLI `--validate-only` require all current notice translations to match this glossary. Missing notice arrays in older minimal test fixtures count as empty; published menu schema still requires the arrays. The glossary translates the source's own labels and does not add independent certification or ingredient claims.

Daily and weekly views preserve language/price-group selection. Dates are interpreted in Europe/Berlin. Show the source coverage and last successful fetch, and make stale/past menus explicit. An update validates data and translations before replacing any published snapshot. Scheduled execution is once each Monday; manual execution is available for recovery and initial deployment.
